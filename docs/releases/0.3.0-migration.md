# LLVM migration for Longreach Qt 0.3.0

Tag `v0.2.2` at `ca04d78` preserves the previous GCC and MinGW SDK
recipes. This migration batch covers 17 SDK targets on upstream LLVM
21.1.8. Four ARM64 targets with runtime validation pending are deferred.

## Repository layout

```text
docker/
  qt4/linux/Dockerfile                 # Sarge i386 and amd64
  qt4/{windows,macos}/<arch>/Dockerfile
  qt5/linux/Dockerfile                 # Lucid i386 and amd64
  qt5/linux/arm64/Dockerfile            # Trusty arm64
  qt5/windows/Dockerfile               # XP i386 and amd64
  qt5/windows/arm64/Dockerfile
  qt5/macos/<arch>/Dockerfile
  qt6/host/Dockerfile                   # shared compiler and native Qt tools
  qt6/{linux,windows,macos}/<arch>/Dockerfile
mk/                                    # public target names and build order
scripts/build/                         # compiler, sysroot and build helpers
scripts/fetch/locks/                   # pinned build and runtime inputs
cmake/                                 # SDK consumer toolchain files
patches/                               # Qt and toolchain compatibility patches
docs/targets/                          # current build and test commands
docs/results/                          # validation and artifact provenance
docs/releases/0.3.0.md                 # release scope and compatibility
```

Each SDK recipe is named `Dockerfile`. Shared recipes select architecture
through build arguments. Use named stages for shared inputs and toolchains,
then build the SDK and its examples against those inputs. Keep shell and
Python helpers under `scripts/`. Preserve the public `make qt<N>-<os>-<arch>`
and `*-examples` commands. Update `build-all`, the Qt 6 coordinator,
image discovery and artifact manifests together. During the migration,
keep LLVM SDK image tags distinct from legacy tags to prevent cache hits
from returning an older SDK.

## Implementation order

1. Build the CentOS 7 input image from the RPM lock and pinned archives.
   Bootstrap the shared compiler from that stage. GCC can bootstrap Clang,
   and target sysroots retain the headers, CRT and startup objects required
   by the minimum OS. Qt and its examples use upstream Clang and LLVM
   runtimes wherever their existing target ABI permits.
2. Migrate and validate Qt 4, then Qt 5. Independent targets for each
   version may build concurrently in small batches with an explicit job
   limit, after their shared dependencies are available. Run test VMs
   one at a time.
3. Separate Qt 6 sysroots, OpenSSL, SDK archives and native Qt tools
   from their legacy SDK images. Verify that each required input can be
   reconstructed on a builder without legacy SDK tags. Build and test the
   Qt 6 SDKs one at a time. Preserve resumable build volumes and the
   existing behavior of `--resume` across cache and path changes.
4. Replace the legacy recipes with the LLVM Dockerfiles as each group
   becomes reproducible. Align their Make entry points, SDK package
   paths, audits, licensing profiles and current documentation.
5. Validate the candidate through its public commands. Run the ordinary
   examples and require all 25 C++23 checks without skips wherever the
   release claims runtime support. Record outstanding ARM64 runtime
   checks and Win95 locale limits explicitly. Tag `v0.3.0` after the
   agreed validation passes.

## Bootstrap validation

The CentOS 7 input stage built from the 197 locked local RPMs and the
pinned source archives. The shared compiler stage built Clang and LLD
21.1.8 using that image. A native C program linked with LLD and ran in
the compiler image. The compiler also produced an AArch64 ELF object.
Neither Qt 6 SDK prefix was present in the compiler image.

Build references `pdni135k6djvz8c501l1d2y2z` for the input stage and
`d27r5ho2icr0gluzvzonffxt9` for the compiler stage. The latter was
validated under `longreach-llvm:21.1.8-compiler-centos7-validation`.

## Qt 4 for Linux

Sarge i386 and amd64 now build through the shared
[`docker/qt4/linux/Dockerfile`](../../docker/qt4/linux/Dockerfile).
The default Make targets use LLVM. The Sarge sysroots and CRT are
reconstructed from pinned packages, and the recipe builds OpenSSL with
Clang. Both QEMU runs passed all eight ordinary applications and the 25
strict C++23 checks without skips. See the [Sarge target guide](../targets/qt4-linux.md)
and [validation record](../results/qt4-linux-sarge-llvm-migration-20261115.json).

## Deferred targets

Windows ARM64 and macOS ARM64 for Qt 5 and Qt 6 are outside this
migration batch. The previous SDK builds for those targets have
compile and binary audit evidence. Their runtime suites require
matching hosts or guests and remain pending.

## Qt 4 for Windows

Windows 95 i386 and XP x64 use separate canonical Dockerfiles and
standard Make targets. Both rebuilt with the new shared LLVM compiler
and the pinned XP toolchain inputs. The ordinary suites and strict
C++23 runs passed in both guests. See the
[Windows target guide](../targets/qt4-windows.md#migration-validation)
and [validation record](../results/qt4-windows-llvm-migration-20261115.json).

## Qt 4 for Mac OS X

Tiger i386 and Jaguar PowerPC now use their canonical Dockerfiles
and Make targets. The build stages reconstruct the Apple SDK inputs,
link tools and OpenSSL separately from Qt. Both use upstream Clang
21.1.8 and libc++ for Qt and applications. Jaguar retains the GCC
driver, libgcc, ABI shims and OpenSSL compiler for its 10.2 ABI.
See the [target guide](../targets/qt4-macos.md) for the build commands.

Tiger 10.4.10 and Jaguar 10.2 in QEMU both passed all eight
ordinary applications and 25/25 strict C++23 checks without skips.
Jaguar also passed the standalone C++23 probe and the QtCore and
QtGui probes. See the results for
[Tiger](../results/qt4-macos-tiger-llvm-migration-20261115.json)
and [Jaguar](../results/qt4-macos-jaguar-llvm-migration-20261115.json).
All six Qt 4 targets have now passed local build and guest validation.

## Qt 5

The default Make targets for Lucid, Trusty ARM64, XP and Intel Snow
Leopard now select the LLVM recipes. Lucid i386 and amd64 share a
Dockerfile and reconstruct the sysroot, optional library stubs,
OpenSSL and the Wayland scanner from their inputs. The Windows XP
targets share the Bionic MinGW-w64 headers and CRT staging recipe.
Trusty consumes a standalone ARM64 LLVM runtime built at the CentOS 7
glibc floor. The Intel macOS targets share the patched Snow Leopard
compiler and stage osxcross separately from Qt.

The standalone ARM64 runtime built from the locked CentOS 7 sysroot
and LLVM 21.1.8. Its C++23 probe passed 25/25 with zero skips under
QEMU user mode, and the ELF audit reported glibc 2.17. BuildKit
reference `ihjcux2kf7p2vvqdr7q4lwbgy` produced
`longreach-llvm:21.1.8-linux-arm64-runtime`. The image contains the
compiler and runtime independently of either Qt SDK.

Both Lucid SDKs rebuilt and passed all eight ordinary applications
and 25/25 strict C++23 checks without skips on Ubuntu 10.04 in QEMU.
The [Lucid record](../results/qt5-linux-lucid-llvm-migration-20261115.json)
includes the ELF 2.10 symbol ceiling and guest fixture details.
The [XP i386 record](../results/qt5-win-i386-llvm-migration-20261115.json)
covers the rebuilt SDK, eight ordinary applications and 25/25 strict
C++23 checks with zero skips on Windows XP SP3. The [XP x64 record](../results/qt5-win-amd64-llvm-migration-20261115.json)
covers eight ordinary applications and strict C++23 25/25 on XP x64 SP2.
All nine AMD64 binaries declare PE subsystem 5.2. Snow Leopard's
compiler and osxcross stages built successfully
under BuildKit references `ned7du6p56fvc8mm94dnpfc6c` and
`imwdi9mrxl28gg31vvoktt4l3`. Clang generated the emulated TLS call
for both i386 and amd64 at the 10.6 deployment floor. The rebuilt Intel
SDKs passed eight ordinary applications and 25/25 strict C++23 checks
without skips on Snow Leopard 10.6.3. The
[Snow Leopard record](../results/qt5-macos-snow-llvm-migration-20261115.json)
includes the Mach-O audit and CMake 3.28.6 retry on i386.

On Trusty ARM64, the first rebuilt SDK passed strict C++23 and seven GUI
examples. The ordinary selftest exposed the QtScript host-return issue
previously seen on XP. Clang folded away the tagged frame test and
the interpreter tried to dispatch from a null return PC. The Trusty
recipe applies the same QtScript fix. The rebuilt SDK passed all eight
ordinary applications and 25/25 strict C++23 checks without skips. The
[Trusty record](../results/qt5-linux-arm64-llvm-migration-20261115.json)
includes the ELF 2.18 ceiling and per-application results.

All seven in-scope Qt 5 targets have now passed build and runtime validation.

## Qt 6

The four in-scope Make routes select LLVM stages in their canonical
Dockerfiles. The native Linux SDK supplies the LLVM host Qt tools.
Cross targets stage the Debian host dependencies, CentOS ARM64 sysroot
or osxcross independently of earlier target SDKs. The sequential
coordinator assembles its prebuilt inputs with the network disabled
and retains its build volumes.

The rebuilt Linux amd64 SDK passed all eight ordinary applications
and 25/25 strict C++23 checks on both Debian 13 and CentOS 7. The
[Linux amd64 record](../results/qt6-linux-amd64-llvm-migration-20261115.json)
records the GLIBC 2.17 ceiling, image and artifact hashes and both
guest runs.

The rebuilt Linux ARM64 SDK passed all eight ordinary applications
and 25/25 strict C++23 checks on CentOS 7 and Debian 12 under QEMU.
The [Linux ARM64 record](../results/qt6-linux-arm64-llvm-migration-20261115.json)
records all nine executable hashes and their GLIBC 2.17 ceiling.

The rebuilt Windows amd64 SDK produced nine PE 6.1 executables.
Windows 7 SP1 passed all eight ordinary applications and 25/25 strict
C++23 checks in an interactive VMware session. An earlier background
run passed strict C++23 and failed the Schannel loopback check.
Windows 11 also passed all eight ordinary applications and all 25
strict C++23 checks. See the [Windows amd64 record](../results/qt6-windows-amd64-llvm-migration-20261116.json)
for the three runs and all nine artifact hashes.

The rebuilt macOS amd64 SDK passed all eight ordinary applications and
25/25 strict C++23 checks on High Sierra 10.13.6. All nine Mach-O
executables declare macOS 10.13 and have no unresolved aligned
allocation symbols. The examples' CMake configuration now omits the
obsolete linker flag -s on Darwin for ld64.lld. See the
[macOS amd64 record](../results/qt6-macos-amd64-llvm-migration-20261116.json).

## Validation complete

All 17 in-scope SDKs passed: six Qt 4, seven Qt 5 and four Qt 6 targets.
Every target ran all eight ordinary applications and all 25 strict
C++23 checks without skips. The reports record optional skips in the
ordinary applications and the runtime limits of the test environments.

## Build-path rechecks

The review rechecked three SDKs one at a time. Qt 4 XP x64 started with
fresh SDK and toolchain tags and `NO_CACHE=1`. Qt 5 macOS amd64 verified
the 10.7 deployment override. Qt 6 Windows amd64 built using a source
archive with a different SHA-256. Repeating each SDK command kept its
image ID and skipped Docker build. The target guides record the inputs
and checks for [Qt 4](../targets/qt4-windows.md#build-path-recheck),
[Qt 5](../targets/qt5-macos.md#deployment-target-recheck) and
[Qt 6](../targets/qt6-windows.md#source-override-recheck).
