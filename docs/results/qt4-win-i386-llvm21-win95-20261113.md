# Qt 4 Windows 95 OSR2 i386 with LLVM 21.1.8

A freestanding C++23 loader probe built with Clang and LLD ran on
Windows 95 OSR2 4.00.1111 under QEMU TCG (Pentium III, 128 MiB). Its
PE subsystem version is 4.0. Its three kernel32 imports resolve against
the OSR2 export snapshot. The guest wrote the expected message and
returned exit code 0. The probe exercises compiler output and the PE
loader. It uses neither libc++ nor Qt.

The separate probe with all 25 C++23 checks linked with static libc++,
libc++abi and libunwind. The trial runtime used the XP i386 headers,
the Win95 executable exit object, a subsystem version of 4.0 and
`VirtualQuery` to locate the loaded image for DWARF unwinding. That
removed the libunwind dependency on PSAPI.

The initial 25-check executable had 35 imports missing from the OSR2
kernel32 and MSVCRT export tables, and 18 direct Unicode imports.
The missing exports include vectored exception handling, file seeking,
aligned allocation and per-locale CRT functions. The runtime also needs
Win9x-compatible implementations for the Unicode file and console
paths. Later builds and guest runs are recorded below.

## Runtime import and first guest run

A second build added a local aligned allocator, older file-seek APIs,
a locale adapter for the original MSVCRT, and winpthreads 4.0.4 rebuilt
with Clang. The OSR2 import audit dropped from 35 missing exports to
zero. The first full C++23 probe started on OSR2, reported C++23 mode
and passed the first eight checks. It stopped at `std::jthread` with
`thread::join failed: No such process`. The thread runtime used
`GetHandleInformation` to validate the thread handle. The next build
uses a zero-time wait to validate the handle and also has zero missing
exports. In QEMU, that build passed the first 15 checks, including
`std::jthread` and `std::stop_token`, then stopped at the temporary-file
setup for `std::print`.

The locale adapter serializes locale changes within libc++ and restores
the process locale after each operation. Win95 MSVCRT has only a
process-wide locale, so concurrent application calls to the CRT
`setlocale` remain outside that synchronization.

The original `VirtualQuery` fallback expected `MEM_IMAGE`. Win95 reports
`MEM_PRIVATE` for the executable, with the correct allocation base.
Accepting that base when it matches the main module restored exception
unwinding. A separate throw-and-catch probe exited successfully on OSR2.

The next full run completed all 25 cases with **22 passed, 3 failed,
0 skipped**. Condition-variable cancellation, the destructor stop/join
path, atomic wait/notify, thread-local destruction, exception unwinding
with RAII and format-error propagation all passed. The failures were
`std::print`, Unicode filesystem round trip and Unicode format/print.
All three reached the same error in the status query for the Windows
temporary directory after `GetTempPathA` returned its path.

The 22-pass executable SHA-256 is
`7ad4430c9de56d193118c7c50b2e76500d395b7f529a92f03a1c9ad56dd8003c`.

A follow-up build routed directory status and creation through the
OSR2 ANSI APIs and rejected names that did not round-trip through the
active file code page. It created the temporary directory, then failed
when opening the Unicode-named file. The full-suite count remained
**22 passed, 3 failed, 0 skipped**. An ANSI conversion alone cannot
represent the mixed Latin and Japanese filename in the Russian guest's
active file code page. [Microsoft Layer for Unicode](https://learn.microsoft.com/en-us/archive/msdn-magazine/2001/october/mslu-develop-unicode-applications-for-windows-9x-platforms-with-the-microsoft-layer-for-unicode).

A separate print probe wrote ASCII and UTF-8 output into a file opened
through the ANSI CRT on OSR2. The byte comparison passed and the process
exited with code 0. This isolates the suite failures to opening the
temporary path used by the print fixture.

A full rerun used an ASCII temporary filename for the two print cases
while keeping their expected output bytes, including the Unicode text.
The independent Unicode filesystem check retained its original mixed
Latin and Japanese filenames. The result was **24 passed, 1 failed,
0 skipped**. The remaining failure was opening the Unicode-named file
for writing. The executable passed the import audit with 193 imports,
zero missing exports and subsystem version 4.0. Its SHA-256 is
`6994664b4068e73e44a6ee6bcef340111c8793ce53ebd14bceb77eb5adb37d0a`.

The repository target `qt4-win-i386-llvm-probe` rebuilt the probe
from pinned LLVM 21.1.8 and winpthreads 4.0.4 sources. The exported
executable repeated **24 passed, 1 failed, 0 skipped** on OSR2, with all
25 names matching the required manifest and no missing PE imports.
Its SHA-256 is
`1a7859bdf24c553a54406940e55a87125ec8ee9b7fbe19feb25b36196855f1cb`.

A separate file API diagnostic recorded ANSI code page 1251 and OEM
code page 866. Converting the original filename through the active ANSI
code page substituted characters and failed a UTF-16 round trip.
`CreateFileW` set error 120 (`ERROR_CALL_NOT_IMPLEMENTED`).
An offline read of the guest volume confirmed that the diagnostic did
not create the requested file. The strict test still requires the
original filename.

## Qt SDK

The repository built Qt 4.8.7 and the examples with qmake 2.01a and
upstream LLVM 21.1.8. The 37 static archive paths match the GCC SDK.
The Win95 Qt profile uses OpenSSL 1.0.2u from the existing Win95 image,
disables SIMD and uses the QtScript interpreter.

The initial example binaries pulled in missing MSVCRT lock exports via
libpng's MinGW `vfprintf`. The final Docker build uses the system
`vfprintf` for Qt's bundled C sources and removes both imports.
The standalone probe and all ten Qt example executables passed
the PE export audit against OSR2 with Winsock 2 and OpenGL installed.
The repeat QEMU run with the clean build passed all eight ordinary applications
with 369 checks passed, zero failed and 155 optional skips. The separate Qt-linked
C++23 selftest ran all 25 required cases and returned **24 passed,
1 failed, 0 skipped**. The failure matched the standalone probe.
All 11 guest executables matched their host SHA-256 values.
The [JSON record](qt4-win-i386-llvm21-win95-20261113.json) lists the
tested files and application results.

## File API follow-up

On the Russian OSR2 guest (4.00.1111), the exact filename failed a
round trip in both installed file API code pages, 1251 and 866.
The guest reported code page 936 as unavailable. A separate host
conversion of the original filename through Windows code page 936
round-tripped without substitution. Microsoft's Windows 95 SDK
documents CP936 as the Simplified Chinese edition's code page.
[Windows 95 local editions](https://techshelps.github.io/MSDN/DNWIN95/HTML/S72F4.HTM).

The same guest probe found that `_wfopen` could not open an existing
ASCII-named file and `MoveFileExA` returned error 120.
`fopen` created the ASCII file and `MoveFileA` renamed it.
The updated libc++ converts representable wide paths before opening
them through `fopen`. Its rename path uses `MoveFileA` when the
`MoveFileExA` stub returns error 120. That fallback can rename to a
free path. It preserves an occupied destination and returns an error
when replacement is unavailable.

The focused C++23 file probe passed on the same Russian OSR2 guest.
It created, renamed and reopened a file whose name contains U+0416,
verified its bytes and size, rejected the original mixed-script name,
and preserved both files when the destination already existed.
Both the focused executable and the rebuilt standalone probe passed
the OSR2 PE export audit. Focused probe SHA-256 is `e90c1b7ce8460f43cf5cbe07aec5e4a8847941fe0f1741dda3f9300eb080ac6b`.
The 25-case test still uses its original filename.

The repository rebuilt the full SDK and examples with the updated
libc++. All 37 static archive paths match the GCC SDK. The 11 PE
executables target subsystem version 4.0 and passed the OSR2 export
audit. All guest executable SHA-256 hashes matched the fresh package.

In QEMU on Russian OSR2, all eight ordinary applications passed
(369 checks passed, zero failed, 155 optional skips).
The standalone probe and SDK-linked selftest each ran all 25
required cases and finished with **24 passed, 1 failed, 0 skipped**.
The single failure was the original mixed-script Unicode filename.
The [JSON record](qt4-win-i386-llvm21-win95-20261113.json) includes
the new SDK image ID and hashes for all 11 files.

## Simplified Chinese OSR2 in QEMU

The [archive copy](https://archive.org/details/Win95OSR2CHS) matched
the archive's published file digest. Its `LAYOUT.INF` lists
`CP_936.NLS` and `UNICODE.BIN`. The 62 setup files were copied to a
separate QEMU disk before running the Chinese Setup wizard, which
reached its OEM product key screen. The QEMU snapshot
`awaiting-oem-key` was restored and displayed the same installer page.
After a restart with QEMU's instruction-count timing enabled, setup
reached the desktop. The guest reported Windows 95 version 4.00.1111
and code page 936 for both ANSI and OEM file operations. The original
mixed-script filename converted without substitution. The standalone
C++23 probe passed **25/25 required checks, with zero skips**, including
opening, renaming and reading that file. The probe used the verified
`msvcrt.dll` from the Winsock 2 package alongside the executable.

The manually added AMD PCnet reported Device Manager code 2. Windows
had no PCI bus enumerator, so the adapter appeared as a root device.
Installing the stock PCI Bus through Add New Hardware enumerated
the AMD PCnet at PCI `1022:2000` and bound Microsoft TCP/IP to it.
The loopback interface responded before and after installing Microsoft
Winsock 2, and the installation log reported success. The network
backend in QEMU used `restrict=on`.

The guest then ran the standalone probe, the SDK-linked strict
selftest and the ordinary suite in sequence. Both C++23 runs passed
**25/25 required checks with zero skips**. The ordinary suite passed
**8/8 applications** with 369 checks passed, zero failed and 155
optional skips. All 11 guest executables matched the SHA-256 values
of the verified test package after extraction from the guest disk.

An offline PE audit resolved every import for the 11 rebuilt i386
executables against 14 system DLLs extracted from the Chinese OSR2
cabinets and the Windows 95 Winsock 2 update. The update supplies
`msvcrt.dll` and `ws2_32.dll`, which are absent from this ISO's
`LAYOUT.INF`. This records the dependency check for the test suite.
